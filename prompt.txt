1. BACKEND CONTEXT (EXISTING CODEBASE)
================================================================================

Project: Crowd surveillance & detection with agitation index (research prototype).
Primary execution: `python main.py` processes frames in a batch (not realtime).

Environment:
- Windows 11, Python 3.10, PyTorch 2.1.2 (CPU now; future CUDA supported)
- Detectron2 built from source, NumPy 1.26.4, OpenCV 4.8.1.78
- matplotlib, tqdm, scipy (Hungarian matching), sqlite3 (built-in)

Core capabilities:
- Multi-model inference (Detectron2):
  - Person detection: Faster R-CNN R50-FPN COCO
  - Pose estimation: Keypoint R-CNN R50-FPN COCO (17 keypoints)
- Tracking: IoU-based + Hungarian matching (designed for future DeepSORT)
- Density intelligence: density_ratio = total_bbox_area / image_area
  - Dynamic crowd classification: Low/Moderate/High Crowd
- Motion modeling: keypoint displacement normalized by torso length
- Abnormal Crowd Motion Detection:
  - AgitationIndex = 0.4*MeanMotion + 0.3*MotionVariance + 0.2*DirectionalVariance + 0.1*DensityChangeRate
  - Dynamic threshold = mean + 2*std (configurable)
- Escalation detection:
  - Event triggers when High Crowd AND AgitationIndex > threshold
  - Saves highlighted frame to output/escalation_frames/
  - Saves event_timeline.json

Outputs generated:
- output/annotated/* (bbox + confidence overlays)
- output/heatmaps/* (Gaussian density heatmap overlays)
- output/metrics.json (per-frame metrics)
- output/summary.json (batch summary)
- output/event_timeline.json (escalation events)
- output/crowd_density_trend.png
- output/agitation_index_trend.png
- output/crowd_analysis.db (SQLite: frames, persons, keypoints tables)
  - keypoints table stores raw keypoints ONLY for escalation-event frames

Project structure:
crowd_project/
  config.py              - Central configuration
  model_registry.py      - Detectron2 model management
  detection_engine.py    - Person detection
  pose_engine.py         - Pose estimation
  tracker.py             - IoU-based tracking
  density_analyzer.py    - Density metrics
  motion_analyzer.py     - Motion modeling
  agitation_analyzer.py  - Agitation index computation
  event_manager.py       - Escalation event detection
  database.py            - SQLite persistence
  analytics.py           - Summary, plots, JSON export
  heatmap.py             - Density heatmap generation
  video_utils.py         - Frame extraction, image loading
  main.py                - CLI orchestrator (FrameProcessor class)

Key configuration (config.py):
- DEVICE (env var CROWD_DEVICE; cpu/cuda)
- MAX_INFERENCE_WIDTH = 960
- DETECTOR_CONFIG = COCO-Detection/faster_rcnn_R_50_FPN_3x.yaml
- POSE_CONFIG = COCO-Keypoints/keypoint_rcnn_R_50_FPN_3x.yaml
- CONFIDENCE_THRESHOLD, POSE_CONFIDENCE_THRESHOLD
- TRACKER_IOU_THRESHOLD, TRACKER_MAX_LOST
- DENSITY_LOW_SIGMA, DENSITY_HIGH_SIGMA
- Agitation weights + AGITATION_THRESHOLD_SIGMA

Batch orchestrator (main.py):
- FrameProcessor class composes all engines
- Pipeline Pass 1: per-frame inference (detection + pose + tracking + density + motion + agitation)
- Pipeline Pass 2: batch classification (density classification + agitation threshold)
- Pipeline Pass 3: event detection and conditional keypoint persistence
- Persists outputs to output/ and prints console report
- Supports --video for frame extraction

================================================================================
3. RECOMMENDED ARCHITECTURE
================================================================================

Create a new web layer (backend API + frontend UI) without breaking the existing CLI:

--- Backend API (Python) ---
- Use FastAPI (preferred) for minimal, research-friendly API
- Add an API service that exposes endpoints to:
  - Upload files (images/video) into a run-specific workspace
  - Start a processing run (calls FrameProcessor programmatically, NOT shelling out)
  - Stream progress (Server-Sent Events or WebSocket) OR polling endpoint
  - List run outputs and provide download endpoints
  - Provide structured JSON for summary, metrics, event timeline
  - Serve images/plots as static files

--- Frontend (Web) ---
- Use React + TypeScript with Vite
- UI must be clean and "gov/research" professional aesthetic
- Pages:
  - Run Creation: upload images/video, configure device, thresholds, weights
  - Run Monitor: progress bar, current frame index, ETA, logs
  - Results: metrics table, filters by classification, events timeline list
  - Visual Review: grid of frames; click to open annotated vs heatmap
  - Analytics: display trend plots
  - Downloads: zip outputs or download individual files

--- Run Management ---
- Each processing request creates a unique RUN_ID (UUID)
- Runs are isolated:
  - input stored under runs/<run_id>/input/...
  - output stored under runs/<run_id>/output/...
  - sqlite db stored under runs/<run_id>/output/crowd_analysis.db
- Progress persisted to runs/<run_id>/status.json for resilience

--- Compatibility ---
- Keep current crowd_project/ pipeline usable via CLI
- API layer should import and use FrameProcessor and existing modules

5. BACKEND API SPECIFICATION
================================================================================

Base: /api

Endpoints:

POST /api/runs
  - multipart form: files[] (images) OR video (single), plus JSON config override
  - returns {run_id, status}

POST /api/runs/{run_id}/start
  - starts processing in background
  - returns {status, message}

GET /api/runs/{run_id}/status
  - returns {run_id, state, progress, current_frame, total_frames,
            started_at, finished_at, error, config}
  - states: created, uploading, processing, completed, failed, cancelled

GET /api/runs/{run_id}/summary
  - returns summary.json content

GET /api/runs/{run_id}/metrics
  - returns metrics.json content

GET /api/runs/{run_id}/events
  - returns event_timeline.json content

GET /api/runs/{run_id}/files
  - returns list of output files with paths and types

GET /api/runs/{run_id}/download?path={relative_path}
  - download any file from run directory

GET /api/runs/{run_id}/artifacts/{name}
  - convenient aliases: /summary.json, /metrics.json, /events.json
  - images: /annotated/{filename}, /heatmaps/{filename}, /escalation/{filename}

POST /api/runs/{run_id}/cancel
  - best-effort cancellation

DELETE /api/runs/{run_id}
  - delete run workspace

GET /api/runs
  - list all runs with summary info

GET /api/health
  - health check, returns {status, device_available, cuda_available}

Processing model:
- Each run executes in a background thread/process managed by FastAPI
- Progress updates written to status.json for resilience
- File serving via FastAPI static file mounting or streaming

Security:
- Sanitize all paths: never allow arbitrary filesystem traversal
- Validate file types and sizes
- UUID-based run isolation

8. IMPLEMENTATION NOTES
================================================================================

Backend Integration:
- Import FrameProcessor from crowd_project.main
- Create a wrapper that adapts FrameProcessor for async operation
- Override output paths per-run by temporarily modifying config values
- Use thread pool for CPU-bound inference
- Stream progress via SSE or polling

Frontend Patterns:
- Container/Presentational component separation
- Custom hooks for API interactions
- Optimistic updates for UI responsiveness
- Error boundaries for graceful failures

Key Design Decisions:
1. FrameProcessor is NOT modified - wrapper adapts it
2. Each run is isolated in its own directory
3. Progress is file-backed for resilience
4. Images served as static files, not base64
5. React Query for caching and synchronization
